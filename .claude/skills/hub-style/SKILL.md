# hub-style — 一套文风，四种文章

hub 里的文章只有四种形态，共用同一条风格底线，只在骨架上不同：

| 形态 | 场景 | 落点（默认私密） | kind |
|---|---|---|---|
| 海报 | 一篇 arXiv 论文精读 | 论文墙 `pages/paper-snapshots/<slug>/` | —（meta.json） |
| 单篇整理 | 非 arXiv 的文章/博客/报告/技术文档精读 | `src/content/vault/<slug>/` | `paper` 或 `reference` |
| 方向综述 | 从种子论文出发覆盖一个方向 | `src/content/vault/<slug>/` | `paper` |
| 实验记录 | 一次具体实验、调试、复现 | `src/content/vault/<slug>/` | `project` |

**一律先落私密。** 进公开 wiki 只走 `publish` skill，且只在用户明确说「发布 / 公开 / 放到 wiki」时。

## 风格底线（四种形态都适用）

1. **只写来源里有的。** 自己的推断、类比、归纳写成「本文的推断：…」（海报用 *inferred*
   标记）。检索不全时写「在本文检索范围内未找到…」，不写「没有任何工作…」。
2. **数字带条件。** 哪个模型、哪个基准、和谁比、样本量；绝对差写**百分点**，相对差写
   **百分比**（「成功率 62%→71%，+9 个百分点」，不是「+9%」）。不利的数字照样写。
3. **术语首次出现**写成「中文名（English）」再补一句人话解释；模型名、数据集名、库名等
   专名不翻译。之后全文用同一个写法。海报例外：双语海报保留英文术语原词，首次出现的非通用术语后补半句
   中文解释。
4. **无主语客观陈述。** 不用「我 / 我们 / 你」（fm-solvers 的教学口吻是旧稿，不再沿用）；
   论文的结论写「X 报告…」，不写「本文提出」。个人判断单独成节，标题就叫「判断」。
5. **禁用空话与论文腔**：显著、大幅、有机融合、三管齐下、具有重要意义、综上所述、
   值得注意的是、不难发现。能换成一个数字或一句具体描述就换。
6. **小标题尽量写成一句结论**（「第一眼看到的证据经常是假的」）；固定骨架里的标签节
   （动机 / 方法 / 实验 / 局限 / References）保留标签。
7. **不手写节号**，也不写「第 N 节」「§3.1」——构建自动编号，章节一挪就错。指代别处用
   标题原文或 `[[slug]]`。
8. **全角标点，引号用「」**，嵌套用『』；正文一段一行，不硬折行。
9. **原图原表不改写成文字**；图的 alt 写成一句说明图意的完整句子（它也是读屏与搜索的文本）。
   局限和负面结果必写，放在它发生的地方或「局限」节。
10. **日期只在 frontmatter**（`created` / `updated`）。实验日期与写作日期不同，在环境表里
    写实验日期。

## 引用格式（综述、单篇整理、需要出处的实验记录）

- 行内：`<sup><a href="#refs">[n]</a></sup>`，按首次出现编号。
- 文末：`<a id="refs"></a>` + `## References`，编号列表，每条：
  `姓, 首字母.（前 3 位 + et al.）. *标题*. 会议/期刊 年份. arXiv:XXXX.XXXXX.`
- 每个 arXiv ID 用 API 核：`curl -s -m 30 "https://export.arxiv.org/api/query?id_list=<id>"`
  （必须 https，每次 sleep 1）。标题、第一作者、年份以 API 为准；核不到的不写。
- 实验记录的出处是代码与日志：写仓库路径 + commit + 行号，或 W&B run 链接。

## 骨架

### 海报（论文墙，单篇 arXiv 论文）

生产细节全在 `pages/paper-snapshots/.claude/skills/paper-poster/SKILL.md`，骨架不变：
hero 概述 2–3 句（含最重要的一个带条件的数字）+ KPI 格 → 01 动机 → 02 方法 → 03 实验 →
04 局限（stated / inferred 分开）。上面的底线 1–9 同样适用，尤其是 2、3、5：KPI 格里的
绝对提升写「+8.8 pp」，不写「+8.8%」。

### 单篇整理（vault 笔记）

与海报同一顺序，写成笔记：

- 开头一段：这篇讲了什么 + 最重要的一个结论（带条件）+ 原文链接。
- 动机：以前卡在哪、为什么难。
- 方法：先一个类比讲通，再按「输入 → 过程 → 输出」走一遍；每个关键设计说清为什么非这么做不可。
- 证据：2–4 个关键数字或论据，各带条件与含义；不利的结果一起列。
- 局限：原文承认的 / 本文推断的，分开。
- 判断：对谁有用、能和哪篇笔记接上（`[[slug]]`）——整节属于推断。
- References（若引用了原文之外的材料）。

### 方向综述（vault 笔记，20–40 篇）

- 开篇：1–3 个具体场景引出问题；一句话主线（标「本文的归纳」）；`> [!tip] 读法建议`。
- 预备知识：5–8 个核心概念的表（中文名（English）/ 一句定义 / 类比）。文末不再重复术语表。
- 简史：时间线，每条一句 + 引用。
- 分类：一张表把方向切成 3–6 条路线（核心想法 / 代表作 / 优点 / 代价）。
- 每条路线一节：问题 → 直觉 → 代表作（每篇 2–5 句，含带条件的关键数字）→ 这条路线没做到什么。
- 评测：常用基准与指标，读数字的陷阱。
- 横向对比表 + 共同规律 + 开放问题（要具体）。
- 延伸阅读（按「先读什么」排序）→ References。

汇总表、加粗句、小结不得比正文结论更强。

### 实验记录（vault 笔记，kind: project）

- 标题写结论或反常现象，不写「XX 实验记录」。
- 开头一段：目标、现场、结论一句话。
- 环境表：代码仓库 + commit、硬件、关键配置、数据、实验日期。
- 正文按推理顺序分节，小标题是一句结论；每节「做了什么 → 看到什么（数字/日志摘录/图）→ 说明什么」。
  坑写在它发生的地方，不集中到文末。
- 结尾三段：**已证实** / **暂时判断** / **仍未知**，再加「下一步」（没有就写「待定」）。
- `> [!note] 这份记录的边界`：核对过什么、没核对什么。

实验资产：图转 WebP（`cwebp -q 80 -resize 1600 0`）放笔记目录 `img/`；日志只截关键段落进正文；
原始日志、权重、数据集、视频不进 git——写本机路径或 W&B 链接。`pnpm check` 的
`check-content-size` 会拦超过 1 MB 的文件和权重/数据格式。

## frontmatter

四个必填词表见 `src/content/notes/_meta/taxonomy.ts`：`kind`（note / paper / project /
reference）、`domains`（第一个是主领域）、`status`（新稿 seedling 或 growing）、`tags`
（小写连字符）。代码核对报告、复现报告归 `project`，速查手册归 `reference`。

## 自查清单（交稿前逐条过）

- [ ] 每个数字有条件，百分点/百分比没混
- [ ] 推断都有标记；汇总句不比正文强
- [ ] 术语首次出现有「中文名（English）」+ 一句解释
- [ ] 没有「我/我们/你」、空话禁用词、`§`、「第 N 节」、手写节号
- [ ] 引号是「」，正文没有硬折行
- [ ] 局限与负面结果写了
- [ ] 引用编号与 References 对得上，arXiv ID 核过
- [ ] `pnpm check` 通过
